AJP stands for Apache JSRF protocol.
And it is a binary protocol which is used between these two servers to communicate instead using
an HTTP protocol.
For example, instead of wasting 12 bytes in every single request for the content type header,
there's a two byte sequence that indicates this header and so on and so on.
So when I send GET to the frontend server, it translates this HTTP request into an AJP packet.
One request, one packet.
Nothing interesting.
The format of the packet looks like this.
First, there are two magic bytes, one, two, three, four.
Next there is the length of the whole AJP packet.
Then there's a byte that says the type of the packet.
In our case, it will always be 02, which means forward request packet.
Then the next one will indicate the HTTP method.
The GET is indicated by code 2 and POST is 4.
Then there's some data about the request like the host, the request URI.
Then there are headers.
And finally, there are some additional parameters.
And that's what happens when we send a GET request without a body.
But what happens when we send a POST?
It gets a bit more interesting because the body of our request is sent separately from
the headers.
So we have one HTTP request but two AJP packets.
And that's a good start if you are looking for request smuggling.
Our goal is to split these two packets so that Tomcat treats the body of our request as a new
request.
It's because the AJP protocol in itself gives us a lot of power.
And in this particular case, we need it to exploit arbitrary file read on Tomcat.
In the packet with headers, there are magic bytes.
Then there's the length of the packet.
And then there is type of the packet and type of the HTTP method.
And I would think that the request body would look similarly.
I would expect magic bytes as well.
I would expect a packet length.
And then I would expect some kind of byte indicating that this packet is a request body.
But it's not the case.
Turns out that in request body, there is no packet type at all.
And the packet length is followed by the data length, which in all packets I've noticed,
was just packet length minus two.
And then there's your whole body, which is forwarded without any modifications.
I didn't read the docs as meticulously when I was solving the challenge.
But when preparing for this video, I saw that even the docs say that this seems like a mistake.
It says how does the Tomcat know if this AJP packet is a request body with length 514 or is it a get forward request?
Tomcat looks at the previous packet.
If it contained the content length header, Tomcat treats the next one as its body.
So every time any AJP packet arrives to Tomcat, it asks a question.
Did the previous packet contain a content length header?
If it didn't, the current packet is a brand new request.
If it did, the current packet is a body.
So if you could trick HTTP to send your body of the request in a situation where the previous
packet will not have the content length header, you will have the AJP request smuggling.
But how do you do this?
If you don't send the content length header at all, you get 400 bad requests and you're
not even talking with Tomcat.
The next idea you might have is to send transfer encoding chunked header.
However, when that happens, Apache HTTP doesn't send the body at all.
I didn't find any piece of the documentation that would explain this behavior, but the comment
in the source code says that the AJP protocol does not want body data yet.
How about an invalid transfer encoding header?
When you do this, you also get 400 bad request.
But when you send transfer encoding chunked, chunked, it's valid enough that you don't get
400 bad request, but it's also not equal to string chunked, which would make HTTP to get
inside the if, which would not send the body.
So when you do this, it forwards the request with this header and then sends your body in
the next AJP packet.
And what does the Tomcat do with the transfer encoding header?
I've looked at the source code of Tomcat and it doesn't even mentioned transfer encoding
header.
So I think it doesn't do anything with it.
All Tomcat does when it sees our body is asking itself a question.
Did the previous request contain a content length header?
And in this case, it didn't.
So our body is processed as a new request.
