In this tutorial we'll cover how to use burp proxy interception rules and all of the associated
options.
Burp proxy is the tool that you can use to intercept, view and modify all the traffic
passing between your browser and the application you're testing.
To see how that works I'm just going to open Burp's embedded browser and visit a URL.
When I do that the requests come through in the proxy intercept view in Burp so that you
can view, modify and forward them.
If you're testing a modern application this can result in a large number of requests and
responses and it can become a bit too much to intercept and view them all and keep having
to click forward.
You can use Burp's interception rules to control exactly what gets intercepted.
We do that in the proxy tool, in the options tab, these settings for intercept client requests
and intercept server responses.
To intercept anything you need to check the box in each section.
By default requests are intercepted, by default responses are not intercepted and you also
need to have your master interception toggle on otherwise everything will get passed through
automatically.
You can define multiple rules to determine what gets intercepted.
Each of these rules can be individually toggled to enable or disable it.
You can have rules set up that you might use from time to time.
You don't have to have them enabled all the time.
The enabled rules are processed in order from top to bottom and the results are combined using
Boolean operators.
And this is a simple left to right logic with no configurable scope.
By default for requests, Burp will intercept requests whose file extension does not match a list of
fairly boring common file extensions for images, style sheets, scripts and other things.
In general, you're less interested in those page resources when you're working.
There are some other rules that are there by default but are not enabled.
So you can say that you will intercept any requests containing parameters or if the HTTP method does
not match the usual get or post, you can enable interception only of items that are in your target
scope.
For responses, the default rule if you enable response interception is that only responses where
the content type header contains the word text will be intercepted.
And there are some other rules which you can use for common purposes.
So if you want to always intercept a response when you modified or intercepted the request,
you can enable these rules.
You can ignore all responses with a 304 status code.
304 status code means to use a local cached copy and this is generally quite a boring response.
And again, you can configure only to intercept responses that are in your target scope.
If you create an interception rule, the way it works is you define the boolean operator that will
be used to combine it with preceding rules and then you pick the attribute that you want to set a rule
for.
So for requests, you have a whole list of different attributes like domain, IP address,
the protocol, method, URL, all these sorts of things.
You can define a rule whether to match on them and you can define does match or does not match
depending on whether you want to intercept.
The match condition can be a regular expression so you've got real flexibility in what kind of items
you match on.
