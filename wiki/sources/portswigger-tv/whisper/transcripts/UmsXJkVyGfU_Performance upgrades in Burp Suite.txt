So table sorting was the first one we looked at.
It was one of the first performance challenges we took on.
So in some very large proxy history tables, some columns could take up to minutes to sort.
And it was made worse by the fact that all of the sorting happened on the swing thread, locking the UI for the entire duration of the sort.
And this was compounded by having the ability to sort by multiple columns at once, meaning that there could be up to three times as many data retrievals as there were for a single column.
So the first and potentially most obvious thing to address was the speed of the sorting itself.
Java's built-in sorting algorithm is pretty well optimized, so instead of looking at that, we address the more problematic speed of data retrieval.
Often the same piece of data would have to be retrieved multiple times in order to complete a sort.
When this is happening from a project file, this can be very slow.
Pre-loading a temporary cache of the data into memory led to much faster access and overall sort durations.
Even though we were able to make the sort operation faster, we still don't want to lock the UI for its duration.
So in order to do this, we had to figure out a way to move the most intensive tasks off the UI thread, which is quite the challenge when you're trying to preserve data integrity on a table.
And finally, we want to let users know that sorting is in progress and that burp hasn't just crashed or given up while it is doing the processing.
So we had to come up with something for that.
So on to the actual solution.
We created a custom implementation of a row sorter, which takes a snapshot of the data to be sorted and pulls it into memory.
We then sort it and apply the calculated indices to the table view and use read-write locking to control access to the table.
The write operations are queued to apply in a batch after the sorting is completed.
